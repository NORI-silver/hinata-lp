# 記事チェックエージェント（どのサイトでも使える手順）

Claude・Codex・ほかのAIが、サイトの記事を **7つの観点** でチェックし、直すための手順です。
サイトごとの違い（記事の場所・ルール・キーワード・必要な情報）は `sites/<site>.json` に書き、この手順には書きません。
2026-10-31 Nori さんの依頼で作成。hinata.shiokonbu.com・shiokonbu.com・pet.shiokonbu.com で使う前提です。

## 7つの観点

| # | 観点 | 何を見るか | 機械（review.py） | AIが見ること |
|---|---|---|---|---|
| 1 | 情報の正確さ | 数字・電話番号・住所・受付時間・固有名詞が公式と合っているか | 電話番号の表示とリンクの食い違い、別の記事と同じ番号、description と本文の金額のずれ、禁止の言い方 | **公式ページを開いて1つずつ照合**（下の「事実の確かめ方」） |
| 2 | リンク | 切れていないか、正しい相手に飛ぶか | サイト内のリンク切れ、別の地域・施設の公式サイトに飛ぶリンク、http、文字のないリンク、（`--external` で）開けない外部リンク | リンク先が **文字どおりのページか**（トップに飛ばされていないか、別の手続きのページでないか） |
| 3 | SEO | 狙う検索語・タイトル・見出し・構造化データ | title・description の長さ、title のキーワード、h1・h2 の数、canonical、ld+json、地名以外同じ description | 検索意図に答える順番か、上位ページにあってうちに無い見出しは何か。**変更案は必ず批判役に通す** |
| 4 | ありきたりでないか | どの記事にも書ける話ばかりでないか | 多くの記事と同じ定型文の割合、この記事だけの文の字数 | その記事にしかない具体（その市の決まり・例外・体験・数字）があるか |
| 5 | 困ったときに必要な情報 | 本当に困った人が次の一歩を踏めるか | サイト設定の「必要な情報」が本文にあるか | 「今日・今週どうすればいいか」が最初の画面でわかるか、電話番号・締め切り・代わりの手があるか |
| 6 | 画像・図 | 文字だけでわかりにくい所に図があるか | 画像・図が0で、図にすると伝わる説明があるページ | どこを図にすると一番伝わるか（大きさの測り方・券の貼り方・流れ・地図など） |
| 7 | 最新か | 古い情報・過ぎた予定が残っていないか | 確認日の古さ、もうすぐ来る変更日、過ぎた日付を「予定」と書いていないか、古い年の資料 | 公式の最新ページ（更新日）と比べる。期限つきの記述は期限の一覧に入れる |

「他の記事より親切で、読みやすくて、行き届いているか」は 3〜6 をまとめた比べ方です。下の「上位ページとの比べ方」でやります。

## 1回の流れ

1. **ルールを読む**：`sites/<site>.json` の `rules`（ファイル）と `rules_tool`（MCPツール）を読む。サイトのルールはこの手順より優先。
2. **記事を集める**：`source` の種類で。
   - `local`：リポジトリのHTML（hinata など）。
   - `sitemap`：公開中のページを sitemap.xml から取る（リポジトリが手元にないサイト）。
   - `wordpress`：MCPの `wp_list_posts` → `wp_get_post` で本文を取り、`<dump_dir>/<slug>.html` に `<article>` で包んで保存してから `local` として読む（shiokonbu.com）。
3. **機械の下調べ**：
   ```
   python3 tools/article_review/review.py tools/article_review/sites/<site>.json [--external]
   ```
   `docs/article-review/<site>-<日付>.md` と `.json` ができる。「AIが深く見る順」の上から見る。
   外部リンクの確認（`--external`）はネットにつながる所（GitHub Actions・手元のMac）で走らせる。
4. **深く見る**（AI）：上位の記事から、1記事ずつ下の「事実の確かめ方」と「上位ページとの比べ方」をやる。見つけたことは次の形で書く。
   ```
   - [重い|中|軽い] 観点番号 記事: 何が違うか（記事の記述 → 公式の記述・URL・確認日）／直し方
   ```
   重い＝読者が損をする・手続きに失敗する誤り（料金・電話・締め切り・持ち込み可否・リンク先違い）。中＝わかりにくい・足りない。軽い＝好み・体裁。
5. **直す**：
   - 事実の誤り・リンク切れ・古い情報（観点 1・2・7）は、公式で確かめたものだけを直し、確認日を更新する。確かめられないものは書き換えず「公式サイトで確認」とする。
   - SEO・構成・新しい欄・図（観点 3〜6）は **案にまとめて批判役に渡す**（下の「批判役」）。残った案だけ実装し、差分をもう一度批判役に見せてから出す。
   - 直す場所はサイト設定の `edit_where` に従う（生成物を手で直さない）。
6. **記録**：サイト設定の `log` に1〜3行。期限つきの記述は `expiry_list` に足す。報告には「直したこと／確かめたけど直さなかったこと（理由）／次に見る記事」を書く。

## 事実の確かめ方

- 記事の **数字・電話番号・住所・時間・URL** を全部抜き出し、出典リンク先（なければ公式サイト内を検索）を開いて照合する。WebFetch などで本文を読み、ページの更新日も見る。
- 公式（自治体・施設・メーカーの公式サイト）だけを根拠にする。まとめサイトや他社の記事は「ほかに書いてある」までで、根拠にしない。
- 合っていれば「確認済み（URL・日付）」、違えば「記事 → 公式」、公式に見当たらなければ「公式で確認できず」と書く。**推測で直さない。**
- 予定の話（〇月から変わる）は、その日が過ぎていないか、もう新しいページが出ていないかを見る。

## 上位ページとの比べ方（ありきたり・親切さ・読みやすさ）

1. その記事の狙う検索語（サイト設定の `keywords`）で検索し、上位3〜5件（公式は除く・除かないの両方）を読む。
2. 次の表を作る。
   | 項目 | うち | 上位A | 上位B | 公式 |
   |---|---|---|---|---|
   | 最初の画面で答えがわかるか | | | | |
   | 困った人の次の一歩（電話・締め切り・代わりの手） | | | | |
   | その記事にしかない具体 | | | | |
   | 図・画像・表 | | | | |
   | 古い・間違いの情報 | | | | |
3. 「上位にあってうちに無いもの」と「うちにしか無いもの」を1行ずつ出す。前者のうち、**読者が本当に困るもの**だけを改善案にする。文字数を増やすための案は出さない。

## 批判役

SEO や構成の変更、新しいページ・欄・図の追加は、案を出した側とは別のエージェントに「批判役」をさせる（`.claude/agents/article-critic.md`。サイトに批判役ツールがあればそれも使う：shiokonbu.com は `critic_review`）。

- 批判役には **案と、読むべきファイル・データ** だけを渡し、案を出した側の結論や「良い案だと思う」は渡さない。
- 案ごとに「採用／修正して採用／保留／棄却」と一番強い反論を出してもらう。反論はデータ（検索数・取れる地域の数・自分のページ同士の取り合い・薄いページ・ルール違反）で。
- 実装後の差分も見せ、`must_fix` を直してから出す。棄却・保留した案と理由も報告に書く。

## 守ること（どのサイトでも）

- 確かめていない数字・体験を書かない。根拠のない実績・件数・「No.1」を書かない。
- 料金・日数・営業時間など変わりうる数字には確認日を残す。
- 元に戻せないこと（外部への送信・決済・本番への直接反映）は、サイトのルールで許されていない限り本人の「やって」を待つ。
- トークン・APIキー・個人のメールアドレスをリポジトリや記事に入れない。

## 新しいサイトで使うとき

1. `sites/` に設定を1つ足す（`sites/hinata.json` が一番くわしい例）。最低限 `name`・`base_url`・`source`・`rules`・`types`。
2. `types[].needs` に「そのサイトの読者が困ったときに必要な情報」を書く。ここがサイトの性格を一番よく表す（hinata＝申込・電話・料金・締め切り、ブログ＝料金・駐車場・営業時間・犬の大きさの条件、など）。
3. 別のリポジトリで使うときは `tools/article_review/` と `.claude/agents/article-*.md` をそのまま写す（Python 3 の標準ライブラリだけで動く）。
